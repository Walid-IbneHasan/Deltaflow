# M5 — Durability and exactly-once

Status: done, 2026-10-19. The argument is in
[`docs/exactly-once.md`](../exactly-once.md). The design choice is
[decision 0005](../decisions/0005-durable-state-checkpoints.md): resume from
checkpointed state (the option chosen at the end of M4), using RocksDB
checkpoints at transaction boundaries.

## What exists

| Module | Contents |
|---|---|
| `sinks/postgres.py` | `PostgresSink("analytics.t")`: net writes per key, one transaction with the watermark, drift checks, replay drop |
| `state/durable.py` | `StateDirectory`: checkpoints with a completion marker, restore by hard link, pruning |
| `runtime/durable.py` | `DurableRunner`: resume or bootstrap, the flush/checkpoint loop, slot ack ≤ checkpoint ≤ watermark |
| `runtime/engine.py` | `metadata()` / `resume=`, plan fingerprint |
| `faults.py` | crash points for the chaos suite (`DELTAFLOW_CRASH_AT=name:n`) |
| `devtools/worker.py` | the durable worker: four views into `analytics.*` |

## Demo

```sh

make worker          # terminal 1; Ctrl-C stops cleanly, kill -9 is fine too
```

### The chaos suite found a real bug

The first run of `flush:after_commit` failed:

```
SinkError: analytics.order_details: delete of (587,) did not match the table (got None);
the table and the view have drifted apart
```

A runner resumed from checkpoint C, with its sinks already written through
W > C. During the replay of (C, W] its periodic flush wrote the watermark at
the engine's frontier, which is below W. That moved the watermark
*backwards*, so the rest of the replay was applied a second time. The sink's
drift check refused the result rather than publishing it.

Fixes:
- a replay flush is a no-op;
- checkpoints use the engine's own frontier;
- `flush` refuses to move a watermark back.

A deterministic regression test
(`test_resume_far_behind_the_sinks_replays_without_applying_twice`) fails
without the fix. Details in exactly-once.md §4.

### The oracle is not vacuous

| Mutation | Result |
|---|---|
| the sink re-applies replays at or below the watermark | random-kill test fails: the worker hits drift and never catches up |
| no replay-flush skip | regression test fails (the watermark guard refuses) |
| re-run `initial()` on resume | engine resume test fails (global aggregate re-created) |

## Other tests

- **Sink logic (unit):**
  - net writes per key;
  - insert, update and delete classification;
  - replay drop at the watermark;
  - non-unique views and wrong columns refused.
- **Sink against Postgres (integration):**
  - writes and watermark commit together;
  - `replace`;
  - four kinds of drift each refused and rolled back with the watermark
    unchanged.
- **Checkpoints:**
  - round trip, isolated from writes made after the restore;
  - pruning;
  - an incomplete checkpoint is ignored;
  - checkpoints move only forward.
- **Engine resume:** at four cut points, a restored engine replays to
  exactly the original deltas. Resuming under different views is refused.
- **Durable runner (integration):**
  - bootstrap, then resume after a clean stop;
  - re-bootstrap when the slot is dropped or the views change;
  - a non-durable sink is refused;
  - the regression test above.

## Found and fixed along the way

**The search_path trap.** Deltaflow's metadata schema was first called
`deltaflow`, the same as the harness's database role. With the default
`search_path` (`"$user", public`), the seed script's unqualified
`CREATE TABLE orders` then landed in `deltaflow.orders`. The metadata schema
is now `_deltaflow`, and the seed schema qualifies `public.`.

## Explicitly not done in M5

- **Sinks in another database than each other.** One flush transaction
  covers all of a runner's sinks; they must share a database.
- **Concurrent writers to sink tables.** Detected as drift, not tolerated.
- **State format migrations.** A view change forces a bootstrap. The plan
  fingerprint covers structure and function names, not function bodies,
  so changing a lambda's logic needs `make worker-reset`. (Since 2026-10-19 a
  changed or added view is rebuilt alone from the checkpoint's source rows,
  without a bootstrap; and a SQL view's fingerprint covers its SQL:
  docs/exactly-once.md, "Changing views without a bootstrap".)
- **Throughput tuning.** The demo's catch-up rate is unexamined until M6.
