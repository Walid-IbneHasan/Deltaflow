# M7 — Scale-out

Status: done, 2026-10-19. Design notes:
[`docs/scale-out.md`](../scale-out.md). Decision:
[0007](../decisions/0007-scale-out.md) (independent shard pipelines,
leases in Postgres, no Raft).

## What exists

| Part | Contents |
|---|---|
| `sharding.py` | `shard_of` (blake2b of the canonical key, mod N), `owner` (rendezvous hashing over live workers) |
| `planner/dsl.py` | `Deltaflow(shards=N, shard_by={...})`; registration refuses views that cannot be merged exactly |
| `planner/merge.py` | merge rules for partials: SQL views (`merge_view_sql`) and Python (`merge_partials`, used by the property test) |
| `state/arrangement.py` | ownership filter: rows moving between shards, keyed by `owns` |
| `sinks/postgres.py` | `shard` column on partial tables; fenced flush (`FOR SHARE` on the lease row, `FencedError`) |
| `runtime/cluster.py` | `ClusterWorker`: heartbeat thread, advisory locks per shard, epoch bump, zombie and previous-owner eviction, slot takeover, rebalancing |
| `devtools/cluster.py` | the demo cluster: four sharded views over six shards, merge views in `analytics_cluster` |

## Demo

```sh
make up && make seed
make cluster-worker ID=w1   # terminal 1
make cluster-worker ID=w2   # terminal 2
make cluster-worker ID=w3   # terminal 3
make load                   # terminal 4
# kill -9 any worker; its shards move to the others within about the TTL (10 s)
make cluster-reset
```

A scripted run of exactly that on this machine (Windows host, Postgres in
Docker, TTL 10 s, load at 60 txn/s). Output is pasted unedited:

```
balanced after 5.5s; leases (shard: owner#epoch): {0: 'w1#2', 1: 'w3#1', 2: 'w3#1', 3: 'w2#1', 4: 'w2#1', 5: 'w1#1'}
kill -9 w1 (owns [0, 5])
re-leased after 10.6s: {0: 'w3#3', 1: 'w3#1', 2: 'w3#1', 3: 'w3#2', 4: 'w2#1', 5: 'w3#2'}
analytics_cluster.orders_per_country          8 rows  equals recompute: True
analytics_cluster.order_details            8776 rows  equals recompute: True
analytics_cluster.order_totals                1 rows  equals recompute: True
analytics_cluster.customer_statuses        3747 rows  equals recompute: True
```

How to read it:

- **The epochs.** `0: 'w1#2'` is shard 0's second owner: w1 took it from
  w3 when w1 joined. After the kill, w3 owns shards 0, 3 and 5, and their
  epochs went up, which fences anything the dead owner had in flight.
- **Shard 3 also moved (w2 → w3), but not because of the kill.**
  Rendezvous gives shard 3 to w3 even with all three workers alive:
  `owner(3, {w1, w2, w3}) = w3`. The script's "balanced" check only
  required three distinct owners, so the snapshot was taken before
  rebalancing had finished. Shard 3 would have moved to w3 anyway. The
  only shards the kill moved were w1's, 0 and 5, as rendezvous
  guarantees.
- **"equals recompute"** compares each merge view with the same query in
  plain SQL over the source tables. The check runs after a marker
  transaction has passed every shard's watermark (24 = 4 views × 6
  shards).

## Tests

| Test | What it checks |
|---|---|
| `tests/unit/test_sharding.py` (5) | hashing is stable and canonical; rendezvous moves only the departed worker's shards |
| `tests/unit/runtime/test_engine_sharded.py` (8) | **merged partials equal the unsharded engine after every transaction**; non-mergeable views refused; moves between shards; unchanged-TOAST move-in refused |
| `tests/integration/test_cluster.py` (2) | a stale-epoch flush writes nothing; a hung lock holder is evicted and its shard taken at epoch 6 |
| `tests/chaos/test_scale_out.py` | acceptance: 3 workers, 6 shards, load, `kill -9` of the busiest worker. Its shards are re-leased, every merge view equals SQL, no row sits on the wrong shard |

Acceptance, last run (TTL 3 s): `failover_s: 3.2`, `problems: []`,
passed in 12.19 s.

Mutations I checked fail the suite:
- **merging `Min` partials with `max()`** fails the acceptance test;
- **keeping moved-out rows on their old shard** fails the property test.

## What testing found

These are written up in [scale-out.md §4](../scale-out.md#4-what-testing-found):

1. **Heartbeats on the event loop made busy workers look dead.** 511 shard
   acquisitions in one start-up. The heartbeat now runs in a thread.
2. **Re-seeding silently emptied the publication.** Set-up now re-adds
   tables.
3. **rocksdict holds the GIL during a checkpoint.** A slow checkpoint
   freezes the whole process, heartbeat thread included. The TTL must
   exceed the slowest checkpoint. This also corrected an M6 claim: running
   the checkpoint in a thread does *not* keep the event loop responsive.
   operations.md and M6.md now say so.
4. **Failover waited on the dead worker's open flush transaction.** It
   took 24.9 s and then 40.8 s against a 10 s TTL. Fixed by tagging every
   connection with `application_name = deltaflow:<worker>`, terminating
   all of a stale worker's sessions, and bumping the epoch under a lock
   timeout. The demo above shows the result: 10.6 s.

## Limits

- **Every shard decodes the whole WAL**: N slots, N decodings, N times the
  snapshot read at bootstrap. Fine at 6–16 shards, not at hundreds.
- **No exchange operator.** Only co-partitioned joins and terminal
  aggregates/distinct can be sharded; the rest is refused at registration.
- **The shard count is fixed** at registration.
- **Takeover resumes from checkpoints only on shared storage.** Otherwise
  the new owner re-bootstraps the shard (correct, slower).
- **Failover is about the TTL plus the resume.** The TTL has to exceed the
  slowest checkpoint (GIL), which on the Windows host means 10 s.
