# M3 — State backend and incremental join

Status: done, 2026-10-18. The design argument and all memory measurements
are in [`docs/join.md`](../join.md). The store choice is
[decision 0004](../decisions/0004-state-store-rocksdb.md): RocksDB, because
only RocksDB lets the process enforce a resident-memory budget.

## What exists

| Module | Contents |
|---|---|
| `state/store.py` | `StateStore`: one RocksDB instance. One LRU cache of `memory_budget` bytes holds data blocks, index/filter blocks and (through a WriteBufferManager) memtables. Lean background work; blob files for values ≥ 4 KiB. Keyspaces, prefix scans, atomic batches, stats. |
| `state/codec.py` | Canonical key encoding: bytes are equal exactly when the values are equal under `==` (Decimal scale, time zones, int/float/Decimal). Prefix-free. Exact value encoding. |
| `state/arrangement.py` | source arrangements, now in the store instead of a dict |
| `operators/join.py` | incremental inner equi-join: two indices, probe-then-fold, NULL keys never match |
| `planner/` | `.join("public.customers", on=("customer_id", "id"))`. Composite keys; chained joins; qualified output columns. Outer and self joins are rejected at registration. |
| `runtime/` | engine owns the store; snapshots stream in byte-bounded chunks; `Runner(..., memory_budget=...)` |
| `observability/memory.py` | resident memory (current and peak) from the OS, stdlib only |

## Acceptance

> A two-table join view matches the equivalent SQL join after every commit,
> across 100k random operations, with resident memory held under the
> configured budget.

### Part 1: after every commit, across 100k operations

Test: `tests/differential/test_join_views.py`.

- Two join views:
  - `orders ⋈ customers` mapped to seven columns, including an md5 of the
    TOASTed bio;
  - pending orders ⋈ customers, filtered on country after the join, with
    a non-injective projection.
- The 1 MiB minimum budget, so state is read back from disk throughout.
- Seed 12345, final code, as run:


### Part 2: resident memory under the budget

Test: `tests/differential/test_memory_budget.py`. The engine runs in a child
process, with 10,000 customers (60% with 8–24 KB bios) and 100,000 orders,
then 3,000 load transactions. As run:

```
budget 32.0 MiB + unbudgeted allowance 32.0 MiB; state on disk 414.6 MiB;
rss baseline 38.7 MiB, after snapshot 72.1 MiB, peak 95.2 MiB (growth 56.6 MiB)
snapshot 5.2s in 68 chunks; source rows {'public.orders': 98531, 'public.customers': 10464};
2856 transactions (2855 committed by the load); view rows 9946
1 passed in 75.05s
```

**What "under the budget" means here, precisely.** The budget bounds
RocksDB's cache, memtables and index/filter blocks. Around it there is a
fixed overhead that does not grow with state:

- the Python heap in flight, measured at 9.7 MiB peak;
- RocksDB allocations outside the cache;
- allocator slack.

The test asserts `peak − baseline ≤ budget + 32 MiB` with the state at 13×
the budget. The supporting measurements are in join.md §6:

- a sweep over budgets of 16–128 MiB, with growth of 44–73 MiB;
- a run with the state doubled to 787 MiB, which added about 8 MiB, all of
  it the in-memory sink holding a view twice the size.

So I am not claiming that RSS ≤ budget. That would be false at small
budgets, and the table shows by how much.

### What measuring found

Both problems below were found by measuring, not by reasoning, and both are
fixed in this milestone:

1. **The M2 snapshot loader read a whole table into a list** before
   installing it. The memory test catches it: restoring the old loader
   gives 161 MiB growth and a failure.
2. **RocksDB's default background settings let its resident memory reach
   3.3× a 16 MiB budget.** Flush and compaction buffers live outside the
   cache, and compaction kept rewriting the 16 KB values. Setting one
   background job, small buffers and blob files for values ≥ 4 KiB brought
   it to 1.3× (measured with a pure-RocksDB script; numbers in join.md §6).

### Other tests

- **Bilinearity property** (`test_join.py`): random insertions and
  retractions on both sides in the same step, NULL keys and duplicates.
  The accumulated output equals a naive join after every step.
- **Engine-level join property** (`test_engine_join.py`):
  - both tables change in one transaction;
  - the join key moves;
  - orphaned orders;
  - unchanged TOAST in right-hand rows.
- **Codec properties:**
  - canonical under `==` across mixed types;
  - the same instant in any zone;
  - trailing zeros beyond 28 digits;
  - prefix-freeness.
- **Store:** state 20× the budget spills to disk and reads back intact.
- **Integration:** the join view against SQL after every change kind,
  including order moves and country changes, under default and FULL
  replica identity.

Mutations tried and caught:

| Mutation | Caught by |
|---|---|
| ignore match multiplicity | join property test |
| never fold the right side | join property test |
| `isoformat` for aware datetimes in keys | codec properties |
| whole-table snapshot loading | memory test |

## Explicitly not done in M3

- **Outer joins, self-joins, joins of two same-named tables.** Rejected at
  registration with a `PlanError`.
- **Projection pushdown below the join.** A joined table's rows are stored
  twice: once in its arrangement, once in the join index.
- **Holding back deltas for inputs that advance independently** (needed
  once sources come from different streams, M7). Today both sides share
  one stream, and a delta older than the folded-in state raises.
- **Durable state.** The store is wiped at start and the WAL is off. M5
  makes state survive restarts atomically with the sink watermark.
- **RSS strictly below the budget.** There is a fixed overhead outside it,
  measured and documented, not hidden.
- **Big transactions.** A single huge transaction is still held in memory
  whole (M1 limitation).
