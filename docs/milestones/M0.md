# M0 — Harness

Status: done, 2026-10-18.

## Demo

```sh
make up      # Postgres 16, wal_level=logical, on localhost:55432
make seed    # recreate customers/orders; 1,000 customers, 10,000 orders (seed=1)
make load    # 2,000 randomized transactions; prints the seed and a replay command
make check   # ruff, ruff format --check, mypy --strict, pytest (needs `make up`)
```

`make load LOAD_ARGS="--txns 0"` runs until Ctrl-C; `--rate 50` throttles to
50 transactions/second; `--seed N` replays a run (after `make seed` with the
same arguments, since the workload depends on the starting state).

Measured on the author's machine (Windows 11, Docker Desktop):

```
$ make seed
seeded customers=1000 orders=10000 seed=1 in 0.31s
$ make load
loadgen seed=1164086519  (replay: make seed && make load LOAD_ARGS='--seed 1164086519 --txns 2000')
start customers=1000 orders=10000
done txns=2000 committed=1904 rolled_back=96 in 10.10s (198 txn/s)
```

This throughput is one connection doing synchronous round trips. It is a
property of the load generator and says nothing about Deltaflow's speed.

## What exists

- **`docker-compose.yml`**: `postgres:16` with `wal_level=logical` and 16
  replication slots and WAL senders. It is published on host port **55432**,
  because 5432 was already taken on the development machine. The port can be
  overridden with `DELTAFLOW_PG_PORT`. A second database, `deltaflow_test`,
  is where the integration tests drop and recreate tables, so they never touch
  demo data.
- **Seed schema** (`deltaflow/devtools/schema.sql`): `customers` and `orders`,
  with `ON DELETE CASCADE` from orders to customers.
- **Workload planner** (`deltaflow/devtools/workload.py`): pure and
  deterministic. It keeps an exact model of both tables. Its mix is chosen to
  cover the cases the M1 decoder must handle:
  - rolled-back transactions (5%) and multi-statement transactions
  - NULLs
  - incompressible 8–24 kB `bio` values, verified to be stored out of line
  - UPDATEs that leave `bio` untouched, which is the case that makes `pgoutput`
    emit the unchanged-TOAST placeholder
  - primary-key UPDATEs
  - cascading deletes
- **Executor** (`deltaflow/devtools/loadgen.py`, `seed.py`). Every statement's
  rowcount is checked against the model. A mismatch raises
  `ModelDivergedError` instead of quietly drifting.
- **CI** (`.github/workflows/ci.yml`): Python 3.12 and 3.14. It brings up the
  same compose file and runs `make check`.

## Tests (20)

- `tests/unit/test_workload.py` (11) covers:
  - determinism, and divergence across seeds
  - rollback isolation in the model
  - FK invariants over 2,000 transactions
  - ids never reused, and recovery from empty tables
  - coverage of every edge case above
  - incompressibility of TOAST values
- `tests/integration/test_postgres_harness.py` (4) checks PG ≥ 16,
  `wal_level=logical`, available slots and senders, and that the role has
  `REPLICATION`.
- `tests/integration/test_seed_and_load.py` (5): the database equals the model
  after seeding, after reseeding, and after an 800-transaction load with
  rollbacks. A seed replays to an identical database. `bio` values really land
  in the TOAST relation.

The integration tests **fail rather than skip** when Postgres is unreachable,
so a green run always means the database was exercised.

Sanity check that the equality oracle is not vacuous: after a load, appending
one character to one toasted `bio` behind the model's back turns the comparison
from `True` to `False`. This was run as a throwaway script, not kept as a test.

## Deliberately not in M0

- Every package except `devtools` is an empty placeholder whose docstring
  names the milestone that fills it.
- `tests/differential/` and `tests/chaos/` do not exist yet. Integration tests
  live in `tests/integration/`, a directory not in the original layout.
- No publication or replication slot is created yet. That belongs to M1.

## Open design fork for M1

**Where does the old row come from on UPDATE/DELETE?** With the default
replica identity, `pgoutput` sends only the primary key of the old row. A view
must retract the *entire* old row, for example to move an order's `amount` out
of the old country's `Sum`. There are two options, and M1 decides between them:
(a) `REPLICA IDENTITY FULL` on source tables, or (b) Deltaflow keeps its own
keyed copy of every source row.
