# M4 — Aggregates

Status: done, 2026-10-18. The design argument, including min/max under
retraction, is in [`docs/aggregates.md`](../aggregates.md).

## What exists

```python
from deltaflow.planner import Count, Deltaflow, Max, Min, Sum

(
    df.view("orders_per_customer")
    .source("public.orders")
    .join("public.customers", on=("customer_id", "id"))
    .filter(lambda r: r["status"] != "cancelled")
    .group_by("customers.country")
    .agg(count=Count(), revenue=Sum("orders.amount"))
    .sink(MemorySink())
)
```

This is the spec's example view, minus the Postgres sink (M5).

| Feature | Notes |
|---|---|
| `.group_by(cols).agg(name=Count() / Count(col) / Sum(col) / Min(col) / Max(col))` | per-group state in the store; emits (old, −1), (new, +1) per changed group |
| `.agg(...)` without group_by | global aggregate: always exactly one row, `(0, NULL…)` when empty |
| `.distinct()` | per-row counts; emits only on 0 ↔ positive transitions |
| min/max under retraction | every value kept per group under an order-preserving key; the extreme is the first/last entry, so deleting it exposes the next |
| exact sums | ints exact; Decimal in a 1000-digit context that traps rounding; floats and bools refused |
| composition | aggregates of joins, filters after aggregates, aggregates of aggregates. A join *after* an aggregation is rejected at registration. |

## Acceptance

> Differential tests per aggregate, including heavy delete workloads.

Test: `tests/differential/test_aggregate_views.py`. Eight views, each with
its SQL, are compared as multisets after every commit:

| View | Covers |
|---|---|
| `orders_per_customer` | the spec's example: join, filter, group_by, Count, Sum |
| `status_extremes` | Count, Sum, Min, Max over `numeric` |
| `customer_activity` | Min/Max over `timestamptz`, `Count(col)`, Sum over a nullable value |
| `country_names` | Min/Max over text (vs `COLLATE "C"`), Max over nullable text |
| `totals` | global aggregate, including over an empty table |
| `customer_statuses` | distinct |
| `countries_with_orders` | distinct after a join |
| `country_size_histogram` | an aggregate of an aggregate |

**Heavy deletes.** The workload runs steady → drain → refill → drain →
refill. Each drain is delete-heavy and runs until the orders table is
**empty** and customers are down to 10. During the drains, about 30% of
steps also delete *on purpose* the row holding a group's current
min or max: the order with a status's extreme amount, or the customer with
a country's extreme name (cascading to its orders).

**The oracle is not vacuous:**

| Mutation | Result |
|---|---|
| keep zero-count min/max entries | differential fails at transaction #1 (`customer_activity`, a stale `first`/`last`); unit property tests fail too |

## Other tests

- **Aggregate property** (`test_aggregate.py`): random changes, with
  removals biased to the group's current min/max, NULL keys and values,
  and Decimal/int mixes. Grouped and global results equal a naive
  recompute after every step.
- **Edge cases:**
  - deleting one of two equal minima;
  - a group emptying, which removes its row;
  - an update that leaves a group's result unchanged, which emits nothing;
  - a batch spanning two times;
  - negative counts, which raise.
- **Exactness:** a 61-digit Decimal sum is exact, and in the same test
  Python's default context gets it wrong. A sum needing more than 1000
  digits raises. Floats and bools are refused.
- **Distinct property**, and **ordered-encoding properties** (order and
  equality preserved across all types).
- **Engine:** a global aggregate over an empty table; a customer moving
  country moves two orders and the max between groups in one transaction.
- **Integration:** a join + group_by view with count/sum/min/max against
  SQL after every change kind, under default and FULL identity.

## Explicitly not done in M4

- **avg, count(distinct), string_agg/array_agg, percentiles.** Not offered
  by the DSL, and anything other than Count/Sum/Min/Max raises at
  registration.
- **Locale collations** for text min/max: code-point order (`COLLATE "C"`)
  only.
- **Float sums.** Refused by design: not associative, so not exactly
  maintainable.
- **Joins after aggregations.** Rejected at registration.
- **Top-k.** Named in the architecture, but not part of any milestone's
  acceptance so far; not implemented.
- **Persisted aggregate results.** Still the in-memory sink; the Postgres
  upsert sink with exactly-once watermarks is M5.
