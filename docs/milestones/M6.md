## Acceptance

> A documented benchmark: sustained changes/second and p99 end-to-end
> freshness on my machine, with the numbers written into the README as
> measured, not as hoped.

Machine: AMD Ryzen 5 5600X (6 cores / 12 threads), 16 GB, Windows 11,
Docker Desktop (WSL2), PostgreSQL 16.15. The workload is the worker's four
views (a join + group_by, a join, a global aggregate, a distinct) over 1,000
customers and 10,000 orders, with exactly-once Postgres sinks and a
checkpoint every 10 s. Method: `benchmarks/throughput.py` docstring and
operations.md.

Two runs, on the same hardware and the same Postgres container:

**Linux.** The benchmark, worker and state run in a Linux container on the
compose network (`benchmarks/results/linux/latest.md`):

| | |
|---|---|
| **sustained changes/second** | **1,603** (438 transactions/s): 20,814 row changes in 12.98 s |

| Load | achieved changes/s | p50 | p90 | **p99 freshness** | max queued | peak RSS | checkpoints (mean, max) |
|---|---|---|---|---|---|---|---|
| 25% | 386 | ≤ 0.075 s | ≤ 0.15 s | **≤ 0.15 s** | 0 | 85.6 MiB | 5 (0.05 s, 0.068 s) |
| 50% | 770 | ≤ 0.075 s | ≤ 0.15 s | **≤ 0.15 s** | 3 | 91.5 MiB | 5 (0.049 s, 0.097 s) |
| 75% | 1,151 | ≤ 0.075 s | ≤ 0.15 s | **≤ 0.2 s** | 16 | 89.4 MiB | 5 (0.077 s, 0.118 s) |

**Windows host.** The benchmark and worker run natively on Windows, with
state on NTFS (`benchmarks/results/windows/latest.md`):

| | |
|---|---|
| **sustained changes/second** | **935** (256 transactions/s): 20,814 row changes in 22.27 s |

| Load | achieved changes/s | p50 | p90 | **p99 freshness** | max queued | peak RSS | checkpoints (mean, max) |
|---|---|---|---|---|---|---|---|
| 25% | 226 | ≤ 0.1 s | ≤ 0.2 s | **≤ 0.75 s** | 27 | 71.6 MiB | 7 (4.329 s, 27.038 s) |
| 50% | 449 | ≤ 30 s | ≤ 30 s | **≤ 30 s** | 32 | 77.7 MiB | 4 (7.094 s, 26.783 s) |
| 75% | 549 | ≤ 0.15 s | ≤ 0.3 s | **≤ 1.0 s** | 32 | 80.0 MiB | 7 (0.539 s, 0.872 s) |

How to read these:

- **Percentiles are bucket upper bounds.** "≤ 0.15 s" means the true p99
  lies at or below 0.15 s.
- **On Windows the load generator, not the engine, set the 75% row's rate.**
  It managed 549 changes/s from one connection, against a target of 701.
- **The Windows 50% row is dominated by one 27 s checkpoint stall.** At
  121 transactions/s, a 27 s stall holds back more than half of a 60 s
  window. The stall comes from the host's file I/O, not from Deltaflow
  (next section). It is reported as measured rather than re-run until a
  lucky window appeared.
- **Freshness spans two clocks**, Postgres's commit time and the worker's
  flush time. Their measured offset was 1.2 ms (Windows) and 0.0 ms
  (Linux container).

## What measuring found

All of these are detailed in operations.md, with the evidence:

1. **Checkpoints at 7.7 s each**, queued behind compactions with one RocksDB
   background job. Two jobs fix it; the M3 memory test still passes (54.9
   MiB growth, limit 64 MiB).
2. **Sink flushes at about 366 ms.** Every pipelined `executemany` cost
   about 45 ms whatever its size. One multi-row statement per kind of
   write instead roughly tripled capacity, from about 420 to about 1,230
   changes/s on Windows.
3. **Freshness counted replayed transactions** after a resume, with their
   old commit times. Fixed: only transactions past the previous watermark
   are samples.
4. **The first backpressure test was vacuous.** A command-line
   `-c wal_sender_timeout` overrode `ALTER SYSTEM`. Fixed, and the test now
   asserts the setting.
5. **Docker Desktop's Windows port forwarding** stops relaying heartbeats
   while the other direction is backed up. The test runs on Linux and is
   skipped on win32; evidence is in operations.md.
6. **Windows host file I/O stalls:** one RocksDB flush took 31 s to write a
   6.7 MB blob file. On Linux, on the same hardware, no checkpoint exceeded
   0.118 s. Most likely on-access antivirus scanning; not proven.
7. **A wrong hypothesis, retracted.** One A/B run blamed the checkpoint
   thread for the stalls; a later direct-call stall disproved it.

## Explicitly not done in M6

- **No authentication** on the monitoring server. It binds to 127.0.0.1;
  put anything else behind a proxy that authenticates.
- **No reconnect inside the runner.** A dropped replication connection ends
  the process; a supervisor restarts it, and M5 makes that exactly-once.
- **No alerting rules or Grafana dashboards.** The metrics are there; the
  rules are not.
- **The Windows host stalls are diagnosed, not fixed.** Excluding the state
  directory from on-access scanning is the user's security decision, and I
  have not changed it.
- **Freshness is end-to-end for this worker only.** It does not include
  WAL replication between servers, if any.
