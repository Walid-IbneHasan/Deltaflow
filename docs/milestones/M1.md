## Demo

```sh
make up && make seed
make tail          # terminal 1: creates publication + persistent slot, prints the stream
make load          # terminal 2
# Ctrl-C tail, run `make load` again, then `make tail`: it resumes where it stopped
make tail-drop     # drop the slot so it stops retaining WAL
make differential  # acceptance test; random seed, printed; DELTAFLOW_SEED=N to replay
```

## Acceptance

> A differential test asserts the decoded stream replayed into an empty table
> reproduces the source table byte-for-byte, including TOASTed and NULL
> columns, over 10k randomized operations.

`tests/differential/test_replication_replay.py`:

1. Seed 300 customers and 2,000 orders.
2. Create a slot that exports a snapshot, and copy the snapshot into
   `replica.*`.
3. Run ≥10,000 randomized statements while concurrently replaying each
   decoded transaction into `replica`.
4. Compare `t::text` for every row in both schemas, and the typed rows against
   the load generator's model.

The test also asserts that the hard cases actually occurred:

- rollbacks
- PK changes
- cascading deletes
- unchanged-TOAST placeholders
- NULLs
- out-of-line values

## Explicitly not done in M1

- **Full old rows for retractions.** The reader passes on what the server
  sends; see the open fork below.
- **Spilling large transactions.** The largest transaction is held in memory.
- **Auto-acknowledging keepalive positions.** An idle reader on a busy server
  retains WAL. This is safe, at the cost of disk.
- **No test of a consumer slower than `wal_sender_timeout`.** The heartbeat
  task is there for that case; testing it is deferred to M6.
- **Protocol v2+, binary tuples, TLS.** Never requested. If the server sends
  those messages anyway, the decoder raises.

## Open design fork for M2: where do full old rows come from?

To retract a row, a view needs every column of the old row, not just its key.
For example, moving an order to another customer must subtract its `amount`
from the old country's `Sum`.

- **(a) `REPLICA IDENTITY FULL` on source tables.** The WAL carries the whole
  old row, and Deltaflow stays stateless at the source. The price is a larger
  WAL record for every UPDATE/DELETE on the *source* database. It also
  requires an `ALTER TABLE` on the user's tables. And unchanged TOAST values
  in the old tuple still need handling.
- **(b) Deltaflow keeps an "arrangement" of each source table, keyed by
  primary key.** This is a stateful source operator: it fills in old rows and
  resolves `UNCHANGED_TOAST` from its own copy. Postgres stays untouched, but
  Deltaflow holds a copy of every source row it reads. This is the M3 state
  backend arriving early, needed from M2.

**Recommendation: (b).** It leaves the user's database alone. It also solves
`UNCHANGED_TOAST` and old-row retraction with one mechanism, the same keyed
state that M3's join indices need anyway. The cost is storage proportional to
the source tables, which M3 bounds by spilling to disk.
